# Versioned Releases Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every publish of the two images gets a SemVer version, image tags `X.Y.Z` / `X.Y` / `latest`, and a GitHub
Release whose notes say what changed; the documentation follows the project style the design describes.

**Architecture:** A `VERSION` file holds `MAJOR.MINOR`; the publish job computes the patch from git tags, the
`latest` images' version labels and registry probes, pushes and tags as today, and hands version, digests and a
content description to a new `release` job (the only one with `contents: write`) that creates the Release
idempotently with `gh`. Release notes are generated by a Python script from this release's manifest and the previous
release's `manifest.json` asset.

**Tech Stack:** bash (`scripts/publish_tested.sh`, `scripts/release.sh`), Python 3 stdlib (`scripts/*.py`,
`unittest`), GitHub Actions, `gh` CLI (preinstalled on runners), Docker/buildx.

**Spec:** `docs/design/2026-11-16-versioned-releases.md` (approved 2026-11-16). Read it first; this plan argues from it.

## Global Constraints

- SemVer `MAJOR.MINOR.PATCH`, one version for both images; first release `0.1.0`; `VERSION` holds `0.1`.
- `VERSION` format: exactly one line matching `^(0|[1-9][0-9]{0,3})\.(0|[1-9][0-9]{0,3})$` (a final newline is
  allowed; CR, spaces, leading zeros, a third component are refused).
- Git tags `vX.Y.Z`; image tags `X.Y.Z` (never moves, never re-used), `X.Y` (moves to the newest patch of its line),
  `latest`. No more date-based tags; tags already published stay untouched.
- Only `latest` and `MAJOR.MINOR` image tags may move; `publish_tested.sh tag` refuses to move anything else.
- Publish iff the content build key differs from a `latest`'s, or the `VERSION` line has no release yet, or
  `force_publish`. No Monday publish, no age-based publish, no `force_skip_check`.
- Next version = highest released patch of the line (git tags and `latest` version labels) + 1, skipping any
  `X.Y.N` a registry already has; none → `X.Y.0`. A `VERSION` line lower than a released version fails the run. The
  registry being unable to tell whether a tag exists fails the run (never guess).
- Order: version → push by digest + same-bits check → sign → attest → image tags → (release job) draft Release →
  upload `manifest.json` → publish Release.
- Only the `release` job has `contents: write`; the `publish` job (registry credentials) never gets it. No new
  third-party actions: GitHub-owned actions and the `gh` CLI only; every `uses:` pinned by full SHA.
- The pipeline never commits or pushes to `main`. `CHANGELOG.md` covers `X.Y.0` releases (hand-written); automatic
  patches are recorded on the Releases page only.
- `manifest.json` is deterministic: same inputs → same bytes (`json.dumps(..., sort_keys=True, indent=2)` + `\n`, no
  timestamps), so a re-run can compare it byte for byte.
- Release notes never exceed 100000 characters (GitHub's limit is 125000).
- The release job is idempotent: it creates what is missing and succeeds when everything exists and matches; anything
  existing that differs (tag at another commit, other manifest) is an error, never overwritten.
- Nothing internal to the maintainers' own deployment in the repository; examples use `example.com`.
- Commits: trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` only. Before every push, run the
  maintainers' internal-names scan over the outgoing diff and commit messages (the controller supplies it; it is never
  written into the repository); it must print nothing.
- Docker for every build and test (Python: `docker run --rm -v "$PWD":/w -w /w python:3.13-slim python3 -m unittest
  discover -s tests -p 'test_*.py'`); no sudo; host ports only from `$PORT_1`..`$PORT_9`; local image builds need
  `--build-context repo=.`; remove every container, image tag and temp file you create. Workflow lint:
  `docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest` (remove the image afterwards).
- Work on branch `release/versions`; do not push until the controller says so (one PR at the end, the owner merges).

## Review Focus

1. A release job re-run after it failed half-way (draft exists without asset; draft with asset; published) must
   complete without a second Release or a changed asset — Task 3, `tests/release_test.sh`.
2. The first release: no previous tag, no previous manifest — notes list the full contents, generate-notes is called
   without `previous_tag_name` — Task 2 unit test + Task 3 stub test.
3. Debian versions with epochs and suffixes (`1:2.39.5-1+deb13u1`, `~`), multi-arch names (`libc6:amd64`), packages
   added or removed between releases — Task 2 unit tests.
4. `VERSION` edge cases (`0.01`, `1`, `0.2.0`, ` 0.2`, CRLF, empty) and git tag lists with non-release tags
   (`v0.1.0-rc1`, `vfoo`, `0.1.0` without `v`) — Task 1 rehearsal/unit assertions.
5. A huge diff (first release, a Debian point release changing 150 packages) staying under the notes cap with a
   pointer to `manifest.json` — Task 2 unit test.

### Task 3: The release job

- Modify: `.github/workflows/build.yml` (publish uploads `manifest.json` as artifact `release-manifest`; new job
  `release`; `report` also needs `release`)

**Interfaces:**
- Consumes: publish outputs `published`, `version`, `edge_digest`, `gen_digest`; `contents.json` (Task 2) in the
  tested-images artifact; `release_notes.py manifest|notes`.
- Produces: `scripts/release.sh VERSION COMMIT MANIFEST NOTES` (env `GH_REPO`, `GH_TOKEN`): ensures Release `vVERSION`

  error. Drafts are not returned by `releases/tags/{tag}`: find them by listing releases.
